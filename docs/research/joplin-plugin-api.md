1. CODEMIRROR CONTENT SCRIPTS (CM6)
====================================================================

Registration API
- `joplin.contentScripts.register(type, id, scriptPath)`. Signature: `public async register(type: ContentScriptType, id: string, scriptPath: string)`. `scriptPath` is relative to the plugin main script. Source: `<J>/packages/lib/services/plugins/api/JoplinContentScripts.ts:41-43` (doc comment 14-40). For a CM6 editor plugin, `type = ContentScriptType.CodeMirrorPlugin` (enum value string `'codeMirrorPlugin'`). Source: `<J>/packages/lib/services/plugins/api/types.ts:960`.
- The enum doc block for `CodeMirrorPlugin` still shows the legacy CM5 template (`plugin`, `codeMirrorResources`, `codeMirrorOptions`, `assets`) and explicitly marks `codeMirrorResources`/`codeMirrorOptions` as "CodeMirror 5 only … ignored on mobile and when the desktop beta editor is enabled." Source: `types.ts:875-960` (esp. 905-918). For CM6 you use `plugin` + `assets` only.

What the content-script module receives (CM6)
- The module's shape is `{ default: function(context) { return { plugin: function(editorControl){…}, assets?: ()=>[…] } } }`.
- `context` object passed to `default()`: `{ postMessage, pluginId, contentScriptId }`. Source: `<J>/packages/editor/CodeMirror/pluginApi/PluginLoader.ts:142-147`; typed as `ContentScriptContext` in `<J>/packages/lib/services/plugins/api/types.ts:646-661`.
- `plugin(editorControl)` is called with the **CodeMirror wrapper object** (`this.editor`, an instance of `CodeMirrorControl`). Source: `PluginLoader.ts:149`. The public plugin-facing shape of that wrapper is the `CodeMirrorControl` interface in `<J>/packages/generator-joplin/generators/app/templates/api/types.ts:683-739`:
  - `editor: any` — the raw CM6 `EditorView`. (line 684-686)
  - `cm6: any` — "Points to a CodeMirror 6 EditorView instance." Used as the **detection flag** to distinguish CM6 from the legacy CM5 emulation; when `editorControl.cm6` is defined you are on CM6. (line 687-688; tutorial confirms the "cm6" flag semantics, https://joplinapp.org/help/api/tutorials/cm6_plugin)
  - `addExtension(extension: any|any[]): void` — the primary hook: adds a CodeMirror 6 `Extension` (or array). Implementation dispatches `StateEffect.appendConfig.of([extension])`. Source interface line 690-692; implementation `<J>/packages/editor/CodeMirror/CodeMirrorControl.ts:306-310`.
  - `registerCommand`, `execCommand`, `supportsCommand` (692-697).
  - `joplinExtensions` — `{ completionSource, enableLanguageDataAutocomplete, noteIdFacet, setNoteIdEffect }`. Notably `noteIdFacet` lets a lint extension read the current note ID; `setNoteIdEffect` lets it react to note switches. Interface 699-738; implementation `CodeMirrorControl.ts:291-304`.
  - Also available on the concrete class (not all in the trimmed public interface): `addStyles(...)` (theme injection, returns `{remove}`), `prependKeymap`, `addExtension`. Source `CodeMirrorControl.ts:228-289`.

CodeMirror 6 libraries available to the content script (do NOT bundle your own)
- The content script may `require(...)` these Joplin-provided CM6 modules; bundling your own copies breaks the editor. Whitelist includes `@codemirror/view`, `@codemirror/state`, `@codemirror/language`, `@codemirror/autocomplete`, `@codemirror/commands`, **`@codemirror/lint`**, `@codemirror/search`, `@codemirror/lang-html`, `@codemirror/lang-markdown`, `@codemirror/language-data`, `@lezer/common`, `@lezer/markdown`, `@lezer/highlight`. Source: `<J>/packages/editor/CodeMirror/pluginApi/codeMirrorRequire.ts`. This is directly load-bearing for Harper: `@codemirror/lint` provides the `Diagnostic`/`linter()`/`setDiagnostics` API and the lint gutter — the idiomatic way to render grammar underlines and quick-fix suggestions. The webpack config marks these as externals; the tutorial imports them "only for type information." (https://joplinapp.org/help/api/tutorials/cm6_plugin)

Where the content script runs (architecturally important)
- On desktop the CM6 editor is instantiated directly into a DOM container in the **main renderer window** via `createEditor(editorContainerRef.current, …)` — NOT in an iframe/sandbox. Source: `<J>/packages/app-desktop/gui/NoteEditor/NoteBody/CodeMirror/v6/Editor.tsx:76`. The content-script JS is served over a custom `joplin-plugin://` protocol and injected as a `<script src>` (see `useContentScriptRegistration.ts:82-95`, and CSP `script-src … joplin-plugin://*` in `<J>/packages/app-desktop/index.html:12`). So the content script executes in Joplin's main renderer process context, under that window's CSP (see §3).

Minimum stable Joplin desktop version
- The official tutorial states the CM6 editor is the default on **Joplin 3.1+** desktop; "on Joplin desktop before version 3.1, the beta editor will need to be enabled in settings > general." (https://joplinapp.org/help/api/tutorials/cm6_plugin). The CM6 "beta editor" and the "expose common CodeMirror packages to plugins" mechanism (PR #9474) landed earlier — CM6 beta first shipped in 2.13 (Dec 2023, https://joplinapp.org/news/20231204-release-2-13/) and the reference snippets plugin declares `app_min_version` 2.14.6. Practical recommendation: set `app_min_version` to **3.1** so `addExtension`/`cm6` are present without requiring the user to toggle a beta setting.

2. MESSAGING: CONTENT SCRIPT ↔ PLUGIN MAIN PROCESS
====================================================================

- From the content script: `const response = await context.postMessage(message);`. It is **async request/response** (returns a Promise that resolves to the plugin's return value). Source: demo `<J>/packages/app-cli/tests/support/plugins/post_messages/src/contentScriptCodeMirror.js:9-10`; type `PostMessageHandler = (message: any)=> Promise<any>` at `types.ts:640-641`.
- In the plugin main process: `joplin.contentScripts.onMessage(contentScriptId, (message) => { … return response; })`. The callback's return value is sent back as the resolved response, enabling two-way comms. Source: `JoplinContentScripts.ts:45-53` and enum doc `types.ts:936-957`.
- Wiring/round-trip: the content script's `postMessage` is bound to `plugin.emitContentScriptMessage(contentScriptId, message)` which returns a Promise. Source `<J>/packages/app-desktop/gui/NoteEditor/NoteBody/CodeMirror/v6/utils/useContentScriptRegistration.ts:57-60`. `emitContentScriptMessage` marshals the call over Electron IPC to the plugin's hidden BrowserWindow (see §3), where the `onMessage` handler runs, then the result is marshalled back. So every call is **two IPC hops across a process boundary** (main renderer ↔ plugin renderer).
- Payload constraints: **JSON-serializable data only.** The official docs state the message "can be any basic JavaScript type (number, string, plain object), but it cannot be a function or class instance." Source: `types.ts:840-842` (MarkdownIt block, same rule applies) and the plugin-runner arg mapping which only special-cases functions→event-ids and otherwise passes plain data (`<J>/packages/app-desktop/services/plugins/plugin_index.js:22-44`; `<J>/packages/app-desktop/services/plugins/PluginRunner.ts:52-90`). No transferables/typed-array zero-copy path is exposed; large strings are copied.

3. WASM IN THE EDITOR WEBVIEW vs. THE PLUGIN MAIN PROCESS
====================================================================

Can the CM6 content script instantiate WebAssembly in the editor view? — Almost certainly NO, blocked by CSP.
- The main window (where the content script runs, §1) sets: `script-src 'self' joplin-plugin://* joplin-content://* ;` with **no `'unsafe-eval'` and no `'wasm-unsafe-eval'`**. Source: `<J>/packages/app-desktop/index.html:6-17` (script-src at line 12).
- Chromium rule: when a page has a CSP, `WebAssembly.compile/instantiate/new WebAssembly.Module` are blocked unless `script-src` (or fallback `default-src`) contains `'wasm-unsafe-eval'` or `'unsafe-eval'` (Chrome 97+). Sources: MDN script-src (https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src), WebAssembly/content-security-policy issue #7 (https://github.com/WebAssembly/content-security-policy/issues/7). Joplin's main-window CSP has neither → Harper's WASM would throw a CSP `CompileError`/`EvalError` in the content script. `default-src 'self'` also constrains `worker-src`, so a Web Worker WASM instance in the editor window is equally blocked.
- Confidence: high on the CSP mechanism; the exact behavior under Joplin's specific Electron/Chromium build should be confirmed empirically. Settling experiment: from a trivial CM6 content script, run `WebAssembly.instantiate(new Uint8Array([0,97,115,109,1,0,0,0]))` (or `new WebAssembly.Module(...)`) and check whether it rejects/throws with a CSP EvalError. If it throws, editor-view WASM is out. (One theoretical escape — relaxing the main-window CSP — is not exposed to plugins and would be a core change, so treat editor-view WASM as unavailable.)

Can the plugin MAIN process run WASM / harper.js? — YES.
- Where the plugin main runs: desktop spawns a **hidden Electron BrowserWindow** with `webPreferences: { nodeIntegration: true, contextIsolation: false }`, loads `plugin_index.html`, and injects the plugin bundle as `<script src="file://…">`. Source: `<J>/packages/app-desktop/services/plugins/PluginRunner.ts:115-139` and `plugin_index.js:164-169`. So the plugin main process is a full **Chromium renderer + Node.js** context.
- `plugin_index.html` has **no CSP** meta tag (`<J>/packages/app-desktop/services/plugins/plugin_index.html` is 5 lines, no CSP), and the window is loaded from a `file://` URL with no session header CSP applied to it. With no CSP, WebAssembly compilation/instantiation and Web Workers are permitted. Therefore harper.js runs here.
- harper.js fit: harper.js is "a copy of Harper's core algorithm compiled to WebAssembly," importable natively in a browser or via npm in Node (https://writewithharper.com/docs/harperjs/introduction). It offers `LocalLinter` (instantiates WASM on the current event loop) and `WorkerLinter` (instantiates WASM inside a Web Worker; recommended for interactive apps to avoid blocking) (https://writewithharper.com/docs/harperjs/linting). A `WorkerLinter` inside the plugin BrowserWindow keeps linting off that renderer's main thread. Harper 2.0 moved the WASM binary to separate importable binary modules for tree-shaking/inlining (https://writewithharper.com/docs/harperjs/ref/harper.js.binarymodule.setup.html), which lets you bundle the `.wasm` with the plugin rather than fetching it at runtime (avoids any network/protocol concern; the plugin window has no CSP anyway).

Recommended architecture and latency
- Run harper.js (WorkerLinter) in the **plugin main process**; the CM6 content script owns a `@codemirror/lint`-style extension that, on a debounced document/viewport change, sends text (or changed ranges) via `context.postMessage`, receives `Diagnostic[]`-shaped results, and paints underlines + quick fixes.
- Round-trip per lint call = serialize text → IPC (main renderer → plugin window) → harper WASM lint → serialize diagnostics → IPC back. Two IPC hops plus JSON (de)serialization of the text and results; harper lint of a paragraph is typically low-tens-of-ms. This is fine for a **debounced** lint (e.g. 300-500 ms idle, or on viewport change), but NOT for literal per-keystroke synchronous calls. Mitigations: debounce; send only the changed range or the visible viewport slice rather than the whole note; keep results small (offsets + message + suggestions); optionally cache by paragraph hash. There is no zero-copy transfer path across the boundary (§2), so keep payloads modest.

4. FILESYSTEM ACCESS (reading e.g. ~/.local/share/harper-dictionary/dictionary.txt)
====================================================================

- Sanctioned/portable API: `joplin.require('fs-extra')` returns Node's `fs-extra` in the plugin main process; this gives full read/write to arbitrary local paths (`readFile`, `pathExists`, etc.). The `require`/`plugins.require` bridge is a **whitelist**: only `sqlite3`, `fs-extra`, and `7zip-bin` are exposed; anything else throws "Module not found." Source: `<J>/packages/app-desktop/services/plugins/plugin_index.js:49-68`. Demo usage: `const fs = joplin.plugins.require('fs-extra'); await fs.pathExists(dir)` at `<J>/packages/app-cli/tests/support/plugins/nativeModule/src/index.ts:31-38`.
- So reading the user's Harper dictionary at an arbitrary absolute path is fully supported via `joplin.require('fs-extra').readFile(path)`. (You'll want `require('os').homedir()` to expand `~`; see next point.)
- Additional (desktop-only) reality: because the plugin window runs with `nodeIntegration: true, contextIsolation: false` (§3), the plugin's own bundled code also has the raw Node `require` in scope, so `require('fs')`, `require('os')`, `require('path')` work directly on desktop. This is how many existing plugins access the FS, but it is not part of the documented/portable API and will NOT work on mobile (§7). Prefer `joplin.require('fs-extra')` for the officially supported path; use `require('os')`/`require('path')` for home-dir expansion knowing it's desktop-only.
- Permission/manifest model: Joplin's manifest has a `permissions` field but the only defined permission today is `PluginPermission.Model = 'model'` (used by the newer AI/model API), and there is **no filesystem permission gate** — FS access is implicitly granted to the plugin process. Manifest fields: `manifest_version, id, name, version, app_min_version, app_min_version_mobile?, platforms?, permissions?, …`. Sources: `<J>/packages/lib/services/plugins/utils/types.ts:1-3` (PluginPermission enum) and `:17-43` (PluginManifest). There is no sandbox confining FS reads to a directory in the current model.
- Content scripts (main renderer) have no direct FS/Node access under CSP; any file read must be done in the plugin main process and the bytes/strings passed back via messaging.

5. SETTINGS API
====================================================================

- Register settings: `joplin.settings.registerSettings(settings: Record<string, SettingItem>)` (call on every plugin start; the older `registerSetting` singular is deprecated). Register a config section with `joplin.settings.registerSection(name, section)`. Read with `joplin.settings.value(key)` / `values(keys)`; write with `setValue(key, value)`. Global (app) settings via `globalValue(s)`. Source: `<J>/packages/lib/services/plugins/api/JoplinSettings.ts:99-213`.
- `SettingItem` supports the types you need: `SettingItemType.Int=1, String=2, Bool=3, Array=4, Object=5, Button=6` (`types.ts:493-499`). Fields include `value, type, label, description, public, section, isEnum, options (value→label map, required when isEnum), secure (stored in system keychain), advanced, minimum/maximum/step, storage (Database|File), subType (FilePath/DirectoryPath — desktop only, "Not supported on mobile")`. Source: `types.ts:502-590`. So: booleans (`Bool`), enums (`String`/`Int` + `isEnum:true` + `options`), strings (`String`), and a directory picker for the dictionary path (`String` + `subType: DirectoryPath`, desktop-only).
- Change events: `joplin.settings.onChange(handler)`. "Triggered with a delay" (debounced) and only fires for your own plugin's keys. Source: `JoplinSettings.ts:213-227`.
- Per-plugin data directory: `await joplin.plugins.dataDir()` returns a persistent per-plugin directory path (created on demand); contrast `installationDir()` which is read-only and may be recreated. Sources: `<J>/packages/lib/services/plugins/api/JoplinPlugins.ts:70-82`. Use `dataDir()` to store a user dictionary/ignore-list or a cached copy of the Harper dictionary.

6. RICH TEXT (TinyMCE) EDITOR — OUT OF SCOPE
====================================================================

Grammar underlines in the Rich Text editor are not viably supported and should be out of scope. `ContentScriptType.CodeMirrorPlugin` targets only the Markdown (CodeMirror) editor; there is no analogous plugin hook that injects decorations/overlays into Joplin's TinyMCE instance. The only plugin surface that touches the RTE is `MarkdownItPlugin`, and only indirectly: it affects rendered HTML, and to survive the RTE's HTML→Markdown round-trip you must wrap output in `joplin-editable`/`joplin-source` metadata elements. Source: `<J>/packages/lib/services/plugins/api/types.ts:785-822`. That mechanism is for custom rendered blocks, not live inline lint underlines, and TinyMCE would strip/normalize arbitrary decoration spans on save. Conclusion: Harper integration should target the Markdown editor only; the RTE is not a supported target for live grammar decorations.

7. MOBILE PLUGIN SUPPORT (future phase only)
====================================================================

- State: Mobile plugin support exists in **beta**, first merged for Android pre-releases in the Joplin 3.x line (tracked in "Mobile: Plugin support" — https://discourse.joplinapp.org/t/mobile-plugin-support/35262; the move to CM6 was explicitly to enable mobile plugins, https://joplinapp.org/news/20240701-release-3-0/). Manifests can mark a plugin desktop-only or mobile-only via `platforms` and set `app_min_version_mobile`. Sources: `<J>/packages/lib/services/plugins/utils/types.ts:23-24`; `<J>/packages/lib/services/plugins/utils/manifestFromObject.ts:61-62,79`.
- CM6 content scripts DO run on mobile: mobile loads the same `ContentScriptType.CodeMirrorPlugin` scripts (as inline `sourceJs`) into its markdown editor, with the same `postMessageHandler → emitContentScriptMessage` bridge. Source: `<J>/packages/app-mobile/contentScripts/markdownEditorBundle/utils/useCodeMirrorPlugins.ts:35-60`. So the CM6 lint-decoration content script is portable in principle.
- Constraints (the hard part for Harper): mobile has **no Node.js and no filesystem** in the plugin runtime — the plugin main process on mobile is a sandboxed WebView, not an Electron/Node renderer, so `joplin.require('fs-extra')`/`require('fs')` and desktop-only setting subtypes (`FilePath`/`DirectoryPath`) are unavailable. WASM feasibility on mobile depends on that WebView's CSP and is unverified here (needs an on-device experiment). Treat mobile as a separate later phase with its own linter-hosting strategy.

UNKNOWNS AND RISKS
====================================================================

- WASM-in-editor-view is inferred-blocked, not empirically proven. The conclusion rests on Joplin's main-window CSP (`script-src` lacking `wasm-unsafe-eval`/`unsafe-eval`, `<J>/packages/app-desktop/index.html:12`) plus the general Chromium rule. Not yet run inside Joplin's exact Electron build. Settling experiment described in §3. If it somehow works, an in-process (no-IPC) architecture becomes possible.
- Plugin-window "no CSP" assumption: verified there is no CSP meta in `plugin_index.html` and it loads from `file://` with no session-level CSP injection found (only `handleCustomProtocols.ts` sets CSP, and that governs the `joplin-content://` protocol, not the plugin window). I did not exhaustively audit every `session.webRequest` handler; low risk but not 100% proven. Confirm by instantiating a trivial WASM module in an `onStart` handler.
- IPC latency numbers are architectural estimates (two IPC hops + JSON serialization), not measured in Joplin. Actual per-lint latency and the right debounce interval should be benchmarked on a representative note. No zero-copy/transferable path exists across the content-script↔plugin boundary, so very large notes could be a serialization cost.
- Exact minimum version where `addExtension`/`cm6` are guaranteed: tutorial says desktop 3.1 default; the API existed in the 2.13-2.14 beta editor. I did not pin the precise commit/version that first shipped `cm6`/`addExtension` on the wrapper. Recommend `app_min_version: 3.1` to be safe.
- Harper 2.0 binary-module API details (which of the "four specialized modules" to import, exact inlined-binary export names, and whether `WorkerLinter` needs a same-origin worker URL) were not fully read from primary docs; npmjs.com returned 403 and some harper docs pages 404'd. Confirm against https://writewithharper.com/docs/harperjs/ (linting, binarymodule.setup) and the Automattic/harper repo before implementation. Whether `WorkerLinter`'s worker bootstrap is compatible with a `file://`-loaded plugin window (worker script origin) is unverified — `LocalLinter` is a guaranteed fallback if the worker path has issues.
- Mobile: WASM feasibility and FS-less linter hosting on the mobile WebView are unverified (no on-device test). `platforms`/`app_min_version_mobile` exist, but treat mobile as an unproven future phase.
- The manifest model has no filesystem-permission gating today (`PluginPermission` only defines `model`); if Joplin later tightens plugin FS permissions, arbitrary reads of `~/.local/share/harper-dictionary/…` could require changes. Low near-term risk.
- LanguageTool plugin's current CM6 status is fluid (active forum discussion); confirm the latest maintained fork/branch before reusing any of its code.
